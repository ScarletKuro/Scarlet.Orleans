# Local benchmark comparison, 2026-11-14–15

All six standard suites were rerun twice across SQLite, PostgreSQL, SQL Server, and MySQL. The retained measurements
ran from **November 14 at 22:57 to November 15 at 00:13, Europe/Tallinn**. There are 12 retained invocations and 132
provider/run rows: **128 complete and four incomplete**. Both repetitions, including failures, are published below.
Filenames use the campaign's November 14 start date.

Follow-up: the [November 15 provider investigation](2026-11-15-provider-investigation.md) identifies and fixes a SQL
Server streaming confirmation deadlock. It also confirms SQLite EF read contention, while the two original caught
transfer exceptions remain unidentified. The historical measurements below predate that provider fix.

The dedicated transactional stores' serialized-payload reduction is consistent, but speed comparisons with grain
storage wrappers depend on the engine and workload. EF Core's throughput cost is much larger for transactions than
for ordinary persistence or reminders. Corrected SQLite concurrency and heartbeat measurements also change how the
older results should be read.

## Setup and interpretation

The measured provider implementations are based on `c9cde1522e1de7741cd9d9741047a78f9448d381`. The code changes in this
rerun affect benchmark scheduling, verification, and connection budgeting. Provider implementation code is unchanged.

| Item | Configuration |
|---|---|
| Host | Windows 11 Pro build 26300; Ryzen 7 5800X3D, 8 cores / 16 logical processors; approximately 64 GiB RAM |
| Containers | Local Docker Desktop, approximately 31.3 GiB available to the VM; no per-container CPU or memory limits |
| Build / runtime | Release, `net10.0`; .NET SDK 11.0.100 and runtime 10.0.15 |
| Packages | Orleans 10.4.0; in-box grain directory and streaming 10.4.0-alpha.1; EF Core 10.0.14; SqlClient 7.1.2 |
| Databases | PostgreSQL 17.11; SQL Server 2022 CU27-GDR / 16.0.4305.5; MySQL 8.4.13; SQLite in WAL mode |
| Connections | `127.0.0.1` with Docker Desktop port mappings; PostgreSQL server limit 100, MySQL limit 500 |
| Durability settings inspected | PostgreSQL `synchronous_commit=on`, `fsync=on`; MySQL `innodb_flush_log_at_trx_commit=1`, `sync_binlog=1` |
| PostgreSQL streaming pools | Maximum 40 connections per provider pool, leaving room under the 100-connection server limit |

An idle MariaDB 11.4.13 container was also running; the standard comparison programs cover SQLite and the three server
engines above. Each invocation creates and removes its own databases. One benchmark executable ran at a time, and each
suite's two retained passes ran consecutively. Engines and providers run in their fixed program order.

These are the six standard comparison modes described in [the benchmark README](../README.md), rather than the optional
soak modes. Most timed concurrent phases last ten seconds. Persistence and transactional state use 1 KiB state, and
streaming has four queues per provider. Storage-contract calls and end-to-end grain/stream workloads measure different
paths; their rates should not be compared across suites.

Each detailed report retains both generated tables. Ranges are the two observed values, not confidence intervals;
percentage comparisons are paired within each run. Two passes can expose large variation, but do not establish
statistical significance. The client and databases share a developer machine, so compare providers within an engine
and workload. These results do not establish production capacity, latency SLOs, or long-running resource stability.

## Measurement corrections

- **Persistence:** the old async loop could let one synchronous SQLite writer consume the entire time window. Writers
  now run independently, the thread-pool minimum is at least 32, and every writer must produce samples.
- **Clustering:** sequential timestamps previously advanced into the future, so the concurrent phase could benchmark
  backwards heartbeats that changed no data. Sequential timestamps now begin an hour in the past; every concurrent
  worker must advance its stored heartbeat. A sufficient worker-thread minimum prevents SQLite calls from starving
  queued workers.
- **Transactions:** total conservation is now checked after spread transfers as well as hot transfers. The existing
  single-account value check remains in place.
- **Streaming:** independent PostgreSQL pools are each capped at 40 connections. Their combined default capacities
  could exceed the server's 100-connection limit and invalidate the comparison. Both providers receive the same budget.

Six preliminary invocations are excluded from the retained tables: two persistence passes before the scheduling fix,
two clustering attempts stopped by the worker/timestamp verification, and two streaming passes that exhausted the
PostgreSQL connection limit. Their raw logs remain in the local artifact directory. After those harness corrections,
the affected suites were run twice again. Workload failures within a retained run remain visible; in particular, the
SQL Server transaction baseline timeout is retained even though its repeat completed.

The earlier SQLite persistence concurrency and clustering heartbeat numbers measure different work from this rerun.
Streaming paced latency also changed in commit `9a12825` on November 14: it now starts at the event's scheduled due time,
including waiting to send. November 12 paced p99 values are therefore not directly comparable. Other historical absolute
timing changes are not controlled old-commit/new-commit experiments, so they should not be called code regressions or
improvements from these measurements alone.

## Reproducing the comparisons

Set `SCARLET_TEST_POSTGRESQL`, `SCARLET_TEST_SQLSERVER`, and `SCARLET_TEST_MYSQL` to administrative connection strings
using `127.0.0.1`. Match the database versions and settings above when comparing absolute numbers. SQLite runs
automatically. Build once, then run each program twice without overlapping benchmark processes:

```powershell
dotnet build Scarlet.Orleans.slnx -c Release
foreach ($suite in 'Persistence', 'Reminders', 'GrainDirectory', 'Clustering', 'Transactions', 'Streaming') {
    foreach ($run in 1..2) {
        dotnet run -c Release --no-build --project "bench/Scarlet.Orleans.$suite.Benchmarks" -- "$($suite.ToLowerInvariant())-run-$run.md"
    }
}
```

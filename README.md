# Scarlet.Orleans

Relational storage providers for [Microsoft Orleans](https://github.com/dotnet/orleans) 10, in two flavours over one
schema: plain **ADO.NET** (NativeAOT compatible) and **EF Core**. Persistence and reminders are available today;
clustering, the grain directory and streaming are planned ([design](community-relational-providers-design.md)).

> **Status: preview.** The packages are tested against every supported engine in CI, including real connection failures
> and the Orleans persistence and reminders TestKits, but have no production deployments yet. Try them where a lost
> write would be annoying rather than catastrophic, and report what you find.

| Package | For |
|---|---|
| [`Scarlet.Orleans.Persistence.AdoNet`](src/Persistence/Scarlet.Orleans.Persistence.AdoNet/README.md) | Grain persistence over ADO.NET. NativeAOT compatible. |
| [`Scarlet.Orleans.Persistence.EntityFrameworkCore`](src/Persistence/Scarlet.Orleans.Persistence.EntityFrameworkCore/README.md) | Grain persistence over EF Core, with the Orleans tables in your own `DbContext` and migrations. |
| [`Scarlet.Orleans.Reminders.AdoNet`](src/Reminders/Scarlet.Orleans.Reminders.AdoNet/README.md) | The reminder table over ADO.NET. NativeAOT compatible. |
| [`Scarlet.Orleans.Reminders.EntityFrameworkCore`](src/Reminders/Scarlet.Orleans.Reminders.EntityFrameworkCore/README.md) | The reminder table over EF Core, in your own `DbContext` and migrations. |

All require .NET 10 and Orleans 10.4 or later. Each package's README covers its setup, schema and options. The two
flavours of a component use the same tables, so either can use a database created by the other, and all components can
share one database and one `orleans_schema_history` table.

## Quick start

```csharp
var dataSource = NpgsqlDataSource.Create(connectionString);

builder.UseOrleans(silo => silo
    .AddScarletAdoNetGrainStorageAsDefault(options =>
    {
        options.DataSource = dataSource;
        options.SchemaMode = SchemaMode.Apply;
    })
    .UseScarletAdoNetReminderService(options =>
    {
        options.DataSource = dataSource;
        options.SchemaMode = SchemaMode.Apply;
    }));
```

`SchemaMode.Apply` creates the tables at startup. In production, have a DBA run the scripts shipped in each package
under `schema/`, and keep the default `Validate`, which checks the schema without needing DDL rights. With EF Core, the
tables come from your own migrations instead.

## Behaviour

- **Optimistic concurrency.** Every grain state write checks the grain's ETag, a GUID generated by the provider, and
  fails with `InconsistentStateException` if another activation wrote first. ETags cannot overflow, and an old one
  matching again is practically impossible. Reminder upserts replace the schedule whatever its ETag, as Orleans
  requires; reminder removes check it.
- **Keys.** Rows are stored under a 128-bit hash of their full identity (service, grain type and key as raw bytes, and
  the state or reminder name), and every read and write verifies the full identity, so grain keys and names of any
  length and content work. A hash collision fails the operation instead of touching another row.
- **Retries.** A write is repeated only when the database reports that the attempt was not applied, such as a deadlock.
  After a broken connection a write's outcome is unknown, so the error surfaces to Orleans instead of being retried into
  a false conflict. In the EF Core flavour, writes ignore the context's execution strategy for the same reason; reads
  use it.
- **Transactions.** Operations run outside any ambient `TransactionScope`, so a caller's rollback cannot undo a write
  Orleans already acted on.
- **Cancellation.** A canceled call does nothing and leaves the state as it was; a write that already committed is
  still reported.

## Diagnostics

Everything is published under the name `Scarlet.Orleans`:

```csharp
builder.Services.AddOpenTelemetry()
    .WithMetrics(metrics => metrics.AddMeter("Scarlet.Orleans"))
    .WithTracing(tracing => tracing.AddSource("Scarlet.Orleans"));
```

| Instrument | Type | Tags |
|---|---|---|
| `scarlet.orleans.persistence.duration` | histogram, seconds | `orleans.storage.name`, `orleans.storage.operation` (`read`, `write`, `clear`), `outcome` (`success`, `conflict`, `collision`, `payload_too_large`, `canceled`, `error`) |
| `scarlet.orleans.persistence.payload.size` | histogram, bytes | `orleans.storage.name` |
| `scarlet.orleans.reminders.duration` | histogram, seconds | `orleans.reminders.operation` (`read`, `read_grain`, `read_range`, `upsert`, `remove`, `clear`), `outcome` (`success`, `collision`, `canceled`, `error`) |
| `scarlet.orleans.retries` | counter | `error` |

Each operation is also a trace span, such as `persistence write` with the grain ID, state name and outcome, or
`reminders upsert`; retries appear as span events. Conflicts are logged at debug level, since concurrent
activations make them normal. Other failures propagate to Orleans, which logs them.

## Supported databases

| Engine | Versions in CI | ADO.NET drivers | EF Core providers |
|---|---|---|---|
| PostgreSQL | 14, 16, 17 | Npgsql | Npgsql.EntityFrameworkCore.PostgreSQL |
| SQL Server | 2019, 2022 | Microsoft.Data.SqlClient | Microsoft.EntityFrameworkCore.SqlServer |
| MySQL | 8.4 | MySqlConnector, MySql.Data | Microting.EntityFrameworkCore.MySql, MySql.EntityFrameworkCore |
| MariaDB | 10.6, 11.4 | MySqlConnector | Microting.EntityFrameworkCore.MySql |
| SQLite | bundled | Microsoft.Data.Sqlite | Microsoft.EntityFrameworkCore.Sqlite |

The EF Core flavour also accepts any other relational provider, on a best-effort basis: its duplicate-key errors are
recognised by their standard SQLSTATE `23505`, or by your own `IsDuplicateKeyError` rule; otherwise the provider checks
for the conflicting row after a failed insert.

**NativeAOT.** The ADO.NET flavour is trimming- and AOT-compatible, and its test suites run as NativeAOT executables
against every engine in CI. An Orleans 10.4 silo itself cannot start under NativeAOT yet, so this guarantee matters once
Orleans supports it. MySql.Data relies on reflection and works under JIT only; use MySqlConnector for AOT.

**MySql.Data over TLS.** Oracle's MySql.Data 26.10 sets up TLS connections through a dictionary it shares without
synchronisation. Many connections opening at once, as when a silo starts under load, can corrupt it, after which every
connection open in the process fails until restart. This is a driver bug, not one in these providers. Prefer
MySqlConnector, which does not have it, or with MySql.Data connect without TLS on a trusted network.
`MySql.EntityFrameworkCore` runs on MySql.Data, so it is affected too; Microting's provider, on MySqlConnector, is not.

## Performance

On the same machine and databases, the ADO.NET persistence flavour matches or beats the in-box Orleans ADO.NET
provider in latency and concurrent throughput on PostgreSQL and SQL Server, and is within run-to-run noise of it on
MySQL. The EF Core flavour costs about 5 to 15% over ADO.NET. See [bench](bench/README.md) to run the comparison on
your own infrastructure.

## Not yet supported

- **Moving from the in-box Orleans ADO.NET providers.** The schemas differ, and there is no import tool yet; start new
  deployments on these providers.
- Table name and schema options; the tables are `orleans_grain_state`, `orleans_reminder` and `orleans_schema_history`
  in the connection's default schema.

## Building and testing

```sh
dotnet build Scarlet.Orleans.slnx
dotnet test --solution Scarlet.Orleans.slnx
```

SQLite tests always run. Each server engine runs when its administrative connection string is set:
`SCARLET_TEST_POSTGRESQL`, `SCARLET_TEST_SQLSERVER`, `SCARLET_TEST_MYSQL`, `SCARLET_TEST_MARIADB`. The tests create and
drop their own databases.
